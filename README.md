## Собственный проект

Тема проекта: каталог космических объектов

Главный класс: `SpaceObject`

Почему этот объект нужен программе: Каждый астрономический объект хранит связанный набор данных — имя, тип, расположение, расстояние, масса, информация. Без класса эти данные пришлось бы держать в отдельных переменных для каждого объекта, что ведёт к дублированию и путанице полей. Класс один раз описывает структуру и позволяет создавать сколько угодно объектов с независимым состоянием.

Какие данные хранит объект:

* `public string Name` — название объекта
* `public string Type` — тип объекта (планета, звезда, чёрная дыра и т.д.)
* `public string Location` — местонахождение объекта относительно Земли
* `public double DistanceLightYears` — расстояние от Земли до объекта (в световых годах)
* `public string Mass` — масса объекта (из-за слишком больших чисел и разных единиц оформлена в виде строки)
* `public string Info` — основная информация об объекте

Какие значения задаются через конструктор: Все шесть полей — имя, тип, расположение, расстояние, масса и заметка — передаются при создании объекта.

Какие значения можно задавать автоматически: Все данные приходят через конструктор.

## Практическая работа №2
### Поведение главного класса

Метод 1: `Approach`
Что делает: Принимает число (приближение в световых годах); отклоняет неположительное значение через ранний `return`; уменьшает расстояние объекта, не позволяя ему уйти в минус (нижняя граница — 0). С этим методом потом создаётся отдельная строка вывода.

Метод 2: `UpdateInfo`
Что делает: Принимает строковое значение и заменяет поле `Info`.

Метод 3: `IsPulsar`
Что делает: Возвращает булево значение `true`/`false` — является ли объект пульсаром. Сравнение выполняется без учёта регистра через `Type.ToLower()`, чтобы `"Пульсар"`, `"пульсар"` и `"ПУЛЬСАР"` распознавались одинаково. На основе этого значения в `Program.cs` выводится статус «уникален / не уникален».

Метод 4: `GetInfo`
Что делает: Возвращает строку-карточку объекта с названием, типом, расположением, расстоянием и массой. Строка не печатается внутри метода — вывод выполняет `Program.cs`.

Почему эти действия относятся именно к этому классу:
Класс `SpaceObject` является моделью реального космического объекта, поэтому он должен сам управлять своим состоянием. Метод `Approach` напрямую изменяет характеристику объекта (его расстояние в зависимости от вводимого приближения) и сам следит, чтобы расстояние не ушло в минус, — это правило относится к состоянию конкретного объекта, а не к программе в целом. Метод `UpdateInfo` заменяет описательные данные объекта. Метод `IsPulsar` проверяет специфическое свойство конкретного объекта на основе его собственного поля `Type`. Метод `GetInfo` собирает карточку из полей того же объекта — формат описания является частью его «паспорта», а не ответственностью `Program.cs`. Вся логика работы с объектом находится в одном месте.

Проверки и полученные результаты:

### Защита состояния Hero

Почему методы ПР №2 не защищали от прямой записи в поле:
Методы `TakeDamage`, `Heal`, `GainExperience` содержали проверки, но поле
`Health` было объявлено как `public int Health;`. Любой код в `Program.cs`
мог записать значение напрямую, минуя метод: `alexander.Health = 5000;`
или `alexander.Health = -100;`. Метод — это просто функция; если данные
открыты, её можно не вызывать. Проверки внутри методов защищали только
действия, которые проходили через эти методы, но не само поле.

Чем отличаются get, set и private set:
- `get` — срабатывает при чтении свойства (`Console.WriteLine(obj.Health);`).
- `set` — срабатывает при записи (`obj.Health = 100;`). В автоматическом
  свойстве `{ get; set; }` доступен внешнему коду, поэтому ничего не
  защищает.
- `private set` — запись разрешена только коду внутри класса `Hero`.
  Чтение снаружи остаётся доступным (свойство объявлено `public`).
  Попытка `obj.Health = -100;` из `Program.cs` даёт ошибку компиляции
  `CS0272`.

Где проверяется начальное здоровье:
В конструкторе `public Hero(string name, int health)`. Сначала вычисляется
`MaxHealth`: если `health <= 0`, предел становится `100`; если `health > 200`,
предел ограничивается `200`. Затем проверяется текущее `Health`: если оно
меньше `0`, ставится `0`; если больше `MaxHealth`, ставится `MaxHealth`.
Порядок важен: сначала подготавливается `MaxHealth`, потом сравнивается
с ним `Health` — иначе сравнивали бы с ещё не готовым пределом.

Как Heal сохраняет границу MaxHealth:
Сначала отбрасывается неположительное лечение (`if (amount <= 0) return;`).
Затем вычисляется `missingHealth = MaxHealth - Health` — сколько здоровья
не хватает до личного предела. Если лечения хватает (`amount >= missingHealth`),
устанавливается `Health = MaxHealth` и метод завершается. Иначе лечение
прибавляется обычным способом (`Health += amount`). При полном здоровье
`missingHealth = 0`, и любое положительное лечение оставит `Health = MaxHealth`.
Сравнение до сложения защищает и от выхода за `MaxHealth`, и от
потенциального переполнения `int`.

Как Name использует поле _name и значение value:
Свойство `Name` — полное: у него есть собственный `get` и `private set`,
а данные хранятся в закрытом поле `private string _name = "Безымянный герой";`.
При чтении `obj.Name` выполняется `get`, который возвращает `_name`. При
присваивании внутри класса (`Name = name;`) выполняется `set`; в нём
доступна автоматическая переменная `value` — это значение правой части
присваивания. Setter проверяет `string.IsNullOrWhiteSpace(value)`: если
имя пустое или из одних пробелов, `_name` становится `"Безымянный герой"`;
иначе `_name = value.Trim()` — пробелы по краям удаляются, а результат
сохраняется. `get` возвращает именно `_name`, а не `Name` — иначе чтение
свойства снова вызвало бы `get` и привело к бесконечной рекурсии.

Почему в конструкторе используется Name = name:
`Name = name;` запускает `set` свойства `Name`, поэтому проходят все
проверки: `Trim()`, замена пустого на «Безымянный герой». Если написать
`_name = name;`, проверки будут обойдены внутри самого класса — это
равносильно прямому присваиванию открытого поля. Конструктор должен
проходить через то же место проверки, что и любое другое присваивание
имени.

## Практическая работа №4

1. **Что хранит элемент List<Hero>?**
   Элемент списка хранит **ссылку** (адрес в памяти) на объект `Hero`, а не сам объект целиком. Сам объект существует отдельно, а список лишь знает, где его найти.

2. **Почему созданный через new Hero(...) объект ещё не в списке?**
   Потому что `new` просто создаёт объект в памяти, но не связывает его со списком. Список — это отдельная сущность. Чтобы он узнал о герое, нужно явно передать ему ссылку через метод `Add()`.

3. **Чем Count отличается от последнего индекса?**
   `Count` — это **количество** элементов (считается с 1). А индексы начинаются с 0. Поэтому индекс последнего элемента всегда на единицу меньше количества: `Count - 1`. Если попытаться взять элемент по индексу `Count`, программа упадёт с ошибкой (выход за границы массива).

4. **Что обозначает hero в foreach (Hero hero in guild.Heroes)?**
   `hero` — это локальная переменная, которая на каждом шаге цикла хранит **ссылку на текущего** героя из списка. Внутри тела цикла `hero` указывает сначала на первого, потом на второго и т.д. Сама переменная `hero` создаётся только для чтения и существует только внутри цикла.

5. **Почему урон через переменную виден и через список?**
   Потому что переменная (например, `first`) и элемент списка (`guild.Heroes[0]`) — это две **разные ссылки, которые ведут к одному и тому же объекту** в памяти. Изменив состояние объекта через одну ссылку (вызвав `TakeDamage`), мы меняем сам объект, поэтому через вторую ссылку тоже видно новое значение.

6. **Что private set у Heroes запрещает, а что пока разрешает?**
   `private set` **запрещает** полностью заменить текущий список на новый извне класса (нельзя написать `guild.Heroes = new List<Hero>();`). Но он **разрешает** изменять содержимое этого списка — добавлять новых героев или дубликаты через `guild.Heroes.Add()`, потому что мы получаем доступ к уже существующему объекту списка и вызываем его методы.

**12. Самостоятельный шаг: кто понесёт ящики**
*Почему `guild.Heroes[0]`, а не «новый герой со здоровьем 0»?*
* Не надо создавать лишний объект.
* Первый герой — уже валидный кандидат, с ним можно сравнивать.
* «Новый со здоровьем 0» — искусственный объект, не принадлежащий гильдии.

*Если у двух одинаковое максимальное здоровье — кто попадёт в `strongest`?*
* Условие > (строго больше) — обновится только на строго большем.
* Значит, останется первый из встреченных максимумов.
* Если бы стояло >= — остался бы последний.

## Практическая работа №5

1. **Кто теперь проверяет повтор при добавлении и почему не Program?**
   Повтор проверяет класс `Guild` (в методе `AddHero`). Если проверка будет в `Program`, она сработает только там, где о ней вспомнили. Любой другой участок кода мог бы добавить героя без всяких проверок. Правило приёма должно принадлежать самому объекту, который хранит этот список.

2. **Когда FindHeroByName возвращает null?**
   Метод возвращает `null`, если запрос пустой или состоит из пробелов, либо если после обхода всего списка не нашлось ни одного героя, чье имя совпадает с запросом (без учета регистра и пробелов).

3. **Зачем очищать запрос, если имена героев уже очищены?**
   Пользователь (или внешний код) может передать в запросе лишние пробелы (например, "  Артём  "). Имена в базе сохранены без пробелов, поэтому чтобы строка `Equals` вернула `true`, нужно очистить именно *входящий запрос* с помощью `Trim()`.

4. **Почему MemberCount не хранит число, а вычисляет его?**
   Это вычисляемое свойство. Оно защищает от рассинхронизации: если мы удалим героя из списка, нам не нужно вручную уменьшать счетчик. `MemberCount` всегда берет актуальное значение `_heroes.Count`.

5. **Удаление из гильдии уничтожает героя?**
   Нет. Удаление (`RemoveHero`) убирает только *ссылку* на героя из списка внутри гильдии. Сам объект в памяти остается живым. Если на него ссылается какая-то переменная в `Program.cs`, мы можем продолжать с ним работать.

6. **Почему private-поле не защищено, если вернуть его из метода?**
   `private` защищает имя переменной от прямого обращения (например, нельзя написать `guild._heroes`). Но если метод возвращает ссылку на этот список (как `return _heroes`), внешний код получает доступ к самому объекту списка и может вызвать `Clear()` или `Add()`. Поэтому методы возвращают наружу *копию* списка.

**Ошибка 1. Поиск сдаётся слишком рано**
```csharp
foreach (Hero hero in _heroes) {
    if (string.Equals(hero.Name, searchName, StringComparison.OrdinalIgnoreCase)) {
        return hero;
    }
    return null;
}
return null;
```
Первым проверяется первый герой в списке, если имя не совпадает, метод сразу возвращает `null` из‑за `return` внутри цикла — до остальных героев цикл не доходит. Чтобы проверить всех, `return null` нужно вынести за пределы `foreach`.
Исправление:
```csharp
foreach (Hero hero in _heroes) {
    if (string.Equals(hero.Name, searchName, StringComparison.OrdinalIgnoreCase)) {
        return hero;
    }
}
return null;
```

**Ошибка 2. Закрытое поле выдали наружу**
```csharp
public List<Hero> GetMembers() {
    return _heroes;
}
```
Проба покажет, что «снимок» и гильдия — один и тот же список: после `GetMembers()` любые изменения снимка (`Add`, `Remove`, `Clear`) сразу меняют гильдию. 
`private` не помог, потому что защищает только поле `_heroes` — снаружи нельзя переприсвоить само поле.
Исправление:
```csharp
public List<Hero> GetMembers() {
    return new List<Hero>(_heroes);
}
```
***

**Самостоятельный шаг: правила переезжают в гильдию**
`CountHealthy` возвращает просто `int`, так как в случае пустой гильдии логично вернуть `0`. `FindStrongest` возвращает `Hero?`, потому что если гильдия пуста, возвращать `0` бессмысленно (нет героя с 0 здоровья), нужно вернуть `null` (отсутствие героя). Вызывающий код обязан проверить `!= null` перед обращением к свойствам.

### Личный проект
**Какой ключ вы выбрали и почему:**
В качестве ключа я выбрал свойство `Name` (имя объекта). Для каталога космических объектов это логично, так как названия уникальны ("Земля", "Sgr A*"). Искать и предотвращать дубликаты по названию — самый естественный способ для этой предметной области.

**В какой ситуации ключ может подвести:**
Ключ по имени может подвести, если в каталог попытаются добавить два разных объекта из разных звездных систем с абсолютно одинаковым названием (например, две разные экзопланеты, которые астрономы назвали одинаково). Программа посчитает их дубликатом и откажется добавлять второй объект, хотя физически это разные вещи.

**Что вернёт поиск и как обрабатывается `null`:**
Метод `FindObjectByName` вернёт `null`, если объекта с таким именем нет в каталоге (или если запрос пустой). В `Program.cs` это обрабатывается через проверку `if (foundObj != null)`. Если объект найден, программа выводит его имя, если нет — выводит сообщение о том, что объект не найден. Это защищает программу от ошибки.
